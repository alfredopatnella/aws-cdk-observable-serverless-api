Observabilidad para una API serverless en AWS

API Gateway → Lambda → CloudWatch → SNS

Aprende cómo los logs estructurados, las métricas personalizadas, los paneles, las alarmas y los runbooks operativos convierten una API serverless simple en algo que los operadores realmente pueden entender y soportar. La API en sí es deliberadamente pequeña -- tres rutas, una función Lambda. La observabilidad es el tema central de este proyecto.

AWS CDK API Gateway Lambda CloudWatch SNS TypeScript

Por qué importa

Desplegar una API no es lo mismo que operarla

Levantar Cliente → API Gateway → Lambda toma muy poco esfuerzo. Responder las preguntas que se hace un operador en el momento en que algo se ve mal requiere un trabajo de diseño real.

¿Está disponible?

Las métricas de tráfico y errores responden esto en segundos, sin adivinar.

¿Está fallando?

Errors de Lambda y 5XXError de API Gateway deberían coincidir entre sí.

¿Se está volviendo más lenta?

Las tendencias de latencia y duración detectan regresiones antes de que los usuarios se quejen.

¿Cuánto tráfico?

Count e Invocations establecen cómo se ve lo "normal".

¿Aislado o generalizado?

Las métricas personalizadas por ruta separan una ruta problemática de un despliegue problemático.

¿Pueden los operadores diagnosticarlo?

Logs estructurados y correlacionados, más un runbook -- no conjeturas.

Arquitectura

Solicitud → telemetría → CloudWatch → alarma → operador

Cada solicitud produce dos flujos paralelos de telemetría que terminan ambos en CloudWatch, el cual alimenta un panel para humanos y alarmas para atención automatizada.

El panel no dispara las alarmas. Ambos son consumidores independientes de los mismos datos de CloudWatch -- las alarmas evalúan las métricas según su propio cronograma, sin importar si alguien tiene el panel abierto o no.

Ciclo de vida de la solicitud

  1. El cliente llama a API Gateway sobre HTTPS.
  2. API Gateway invoca a Lambda mediante una integración proxy.
  3. Lambda captura el contexto de la solicitud (ID de solicitud, ruta, método).
  4. Lambda emite logs JSON estructurados.
  5. Lambda emite métricas personalizadas de la aplicación (EMF).
  6. AWS publica automáticamente las métricas de Lambda.
  7. AWS publica automáticamente las métricas de API Gateway.
  8. CloudWatch almacena y agrega todo.
  9. El panel visualiza el estado operativo actual bajo demanda.
  10. Las alarmas evalúan los umbrales de forma independiente, según su propio período.
  11. Un cambio de estado de una alarma publica una notificación a SNS.

Registro estructurado

Cada línea de log es un objeto JSON, no una frase

Una línea de log estructurada se puede filtrar, agregar y correlacionar con CloudWatch Logs Insights. Una frase de texto libre solo se puede leer.

Sin estructura
Request successful
Estructurado
{
  "level": "INFO",
  "message": "Request completed",
  "requestId": "abc-123",
  "route": "/work",
  "statusCode": 200,
  "durationMs": 245
}

Identificadores de correlación

Cada línea de log incluye requestId, tomado del ID de solicitud de API Gateway. Una solicitud, un identificador, cada línea de log relacionada etiquetada con él -- la base de la consulta de Logs Insights "encuentra todo sobre esta solicitud" que se muestra más abajo.

Tres niveles, a propósito

INFO para finalización normal, WARN para entradas inesperadas pero manejadas, ERROR para solicitudes fallidas. Sin un framework elaborado de niveles de logging.

Lo que nunca se registra

Headers de autorización, credenciales, headers completos de la solicitud, o payloads sin procesar del usuario. Registro estructurado significa contexto operativo útil en una forma predecible -- no "registrar todo."

Métricas

Tres categorías, mantenidas deliberadamente separadas

AWS publica algunas métricas automáticamente. La aplicación publica un pequeño número de métricas personalizadas. Ambas viven en CloudWatch, mapeadas más abajo a las categorías de señales doradas.

Tráfico

  • API Gateway Count
  • Lambda Invocations

Latencia

  • API Gateway Latency
  • Lambda Duration

Errores

  • API Gateway 5XXError
  • Lambda Errors
  • Personalizada FailedRequests

Aplicación

  • Personalizada WorkDuration
  • Personalizada SuccessfulRequests

Administradas por AWS vs. personalizadas

OrigenEjemplosCómo se produce
Administradas por AWS (Lambda) Invocations, Errors, Duration, Throttles, ConcurrentExecutions Publicadas automáticamente — no requiere código de la aplicación
Administradas por AWS (API Gateway) Count, Latency, IntegrationLatency, 4XXError, 5XXError Publicadas automáticamente para la REST API y el stage
Métricas personalizadas de la aplicación SuccessfulRequests, FailedRequests, WorkDuration Líneas de log en Embedded Metric Format (EMF), namespace ObservableServerlessApi

Las dimensiones de las métricas personalizadas se limitan a Environment y Operation (tres valores fijos). Nunca uses requestId, userId, o email como dimensión — cada valor único se convierte en su propia serie temporal de métrica, facturable y permanente.

Panel de CloudWatch

Una vista operativa curada, no un catálogo de métricas

El panel desplegado (<stack-name>-observability) está organizado en tres filas. Las tarjetas de abajo son un resumen conceptual de lo que muestra — el panel de CloudWatch desplegado es la fuente autoritativa en vivo.

Salud de la API

  • API Requests
  • API Latency
  • API 4XX / 5XX Errors

Salud de Lambda

  • Lambda Invocations
  • Lambda Errors
  • Lambda Duration + Throttles

Métricas de la aplicación

  • Successful Requests
  • Failed Requests
  • Application Work Duration

Alarmas de CloudWatch

Una alarma solo es útil si es accionable

Una alarma sin un procedimiento de respuesta claro es ruido operativo. Cada alarma aquí es intencionalmente sensible con fines de demostración, y cada una enlaza a un runbook.

Cada alarma usa un período de 1 minuto, 1 período de evaluación, y trata los datos faltantes como notBreaching — un minuto sin actividad en una API de demostración de bajo tráfico no es evidencia de un problema. Las cuatro notifican a un único topic de SNS.

Mecanismos de demostración

Genera señales reales a demanda

GET /work admite dos parámetros de consulta que existen únicamente para demostración y pruebas — nunca expongas en una API real un interruptor de fallo/retraso controlado por quien llama.

Simulación de latencia

GET /work?delayMs=2000

El handler espera un retraso acotado, limitado del lado del servidor a un máximo de 5000ms, antes de responder. Hace subir API Latency y Lambda Duration durante ese minuto.

Simulación de fallo

GET /work?fail=true

El handler registra una entrada ERROR estructurada, y luego lanza una excepción. Esto produce un punto de datos de Errors en Lambda y un 502 de API Gateway (contabilizado en 5XXError) — un solo fallo simulado, dos señales reales.

CloudWatch Logs Insights

Consulta los logs estructurados directamente

Estas consultas coinciden con los campos de log JSON mostrados más arriba.

Errores, más recientes primero

fields @timestamp, requestId, message, route, statusCode
| filter level = "ERROR"
| sort @timestamp desc
| limit 50

Solicitudes lentas

fields @timestamp, requestId, route, durationMs
| filter durationMs > 1000
| sort durationMs desc
| limit 50

Una solicitud, la historia completa

fields @timestamp, level, message, requestId, route, durationMs
| filter requestId = "REQUEST_ID_HERE"
| sort @timestamp asc

Notificaciones de SNS

Las alarmas notifican a un único topic de SNS

No hay ninguna dirección de correo codificada de forma fija en este proyecto. Suscribe una de forma opcional al momento del despliegue: 

npx cdk deploy -c alarmEmail=you@example.com

Las suscripciones por email de SNS requieren confirmación. Revisa la bandeja de entrada en busca de un enlace de confirmación — no se entregan notificaciones hasta hacer clic en él.

Una alarma dice que algo está mal. Un runbook dice qué hacer.

Costos y preparación para producción

La observabilidad tiene un costo — y un límite hasta dónde llega esta muestra

Factores de costo

Solicitudes a la API, invocación/duración de Lambda, ingesta y almacenamiento de CloudWatch Logs, almacenamiento de métricas personalizadas, un panel, cuatro alarmas, notificaciones de SNS. Más telemetría no es automáticamente mejor telemetría — ver docs/es/cost-considerations.md.

Recomendado para producción

Autenticación, WAF, alarmas por tasa de error (no absolutas), latencia p90/p95/p99, SLOs/SLIs, trazabilidad con AWS X-Ray u OpenTelemetry, registro centralizado, integración con herramientas de gestión de incidentes. Ver sección de producción del README.

Pruébalo tú mismo

Ejecuta el ciclo completo en unos pocos comandos

npx cdk deploy

curl "$API_URL/health"
curl "$API_URL/hello"
curl "$API_URL/work?delayMs=2000"
curl "$API_URL/work?fail=true"

Luego abre el panel de CloudWatch, consulta los logs, observa disparase una alarma, y sigue el runbook correspondiente.
