Observability for a Serverless AWS API

API Gateway → Lambda → CloudWatch → SNS

Learn how structured logs, custom metrics, dashboards, alarms, and operational runbooks turn a simple serverless API into something operators can actually understand and support. The API itself is deliberately tiny — three routes, one Lambda function. Observability is the subject of this project.

Why it matters

Deploying an API is not the same as operating one

It takes very little to stand up Client → API Gateway → Lambda. It takes real design work to answer the questions an operator asks the moment something looks wrong.

Is it available?

Traffic and error metrics answer this in seconds, not by guessing.

Is it failing?

Lambda Errors and API Gateway 5XXError should agree with each other.

Is it getting slower?

Latency and duration trends catch regressions before users complain.

How much traffic?

Count and Invocations establish what "normal" looks like.

Isolated or widespread?

Per-route custom metrics separate a bad route from a bad deployment.

Can operators diagnose it?

Correlated, structured logs plus a runbook — not guesswork.

Architecture

Request → telemetry → CloudWatch → alarm → operator

The dashboard does not trigger the alarms. Both are independent consumers of the same CloudWatch data — alarms evaluate metrics on their own schedule whether or not anyone has the dashboard open.

Request lifecycle

  1. Client calls API Gateway over HTTPS.
  2. API Gateway invokes Lambda via a proxy integration.
  3. Lambda captures request context (request ID, route, method).
  4. Lambda emits structured JSON logs.
  5. Lambda emits custom application metrics (EMF).
  6. AWS automatically publishes Lambda metrics.
  7. AWS automatically publishes API Gateway metrics.
  8. CloudWatch stores and aggregates all of it.
  9. The dashboard visualizes current operational health on demand.
  10. Alarms evaluate thresholds independently, on their own period.
  11. An alarm state change publishes a notification to SNS.

Structured logging

Every log line is a JSON object, not a sentence

A structured log line can be filtered, aggregated, and correlated with CloudWatch Logs Insights. A free-text sentence can only be read.

Unstructured
Request successful
Structured
{
  "level": "INFO",
  "message": "Request completed",
  "requestId": "abc-123",
  "route": "/work",
  "statusCode": 200,
  "durationMs": 245
}

Correlation IDs

Every log line includes requestId, taken from the API Gateway request ID. One request, one identifier, every related log line tagged with it — the basis for the "find everything about this request" Logs Insights query below.

Three levels, on purpose

INFO for normal completion, WARN for handled-but-unexpected input, ERROR for failed requests. No elaborate logging-level framework.

What's never logged

Authorization headers, credentials, full request headers, or raw user payloads. Structured logging means useful operational context in a predictable shape — not "log everything."

Metrics

Three categories, deliberately kept distinct

AWS publishes some metrics automatically. The application publishes a small number of custom metrics. Both live in CloudWatch, mapped below to the golden-signal categories.

Traffic

  • API Gateway Count
  • Lambda Invocations

Latency

  • API Gateway Latency
  • Lambda Duration

Errors

  • API Gateway 5XXError
  • Lambda Errors
  • Custom FailedRequests

Application

  • Custom WorkDuration
  • Custom SuccessfulRequests

AWS-managed vs. custom

SourceExamplesHow it's produced
AWS-managed (Lambda) Invocations, Errors, Duration, Throttles, ConcurrentExecutions Published automatically — no application code required
AWS-managed (API Gateway) Count, Latency, IntegrationLatency, 4XXError, 5XXError Published automatically for the REST API and stage
Custom application metrics SuccessfulRequests, FailedRequests, WorkDuration Embedded Metric Format (EMF) log lines, namespace ObservableServerlessApi

Custom metric dimensions are limited to Environment and Operation (three fixed values). Never use requestId, userId, or email as a dimension — each unique value becomes its own billable, permanent metric time series.

An alarm is only useful if it's actionable

An alarm without a clear response procedure is operational noise. Every alarm here is intentionally sensitive for demonstration purposes, and every one links to a runbook.

Every alarm uses a 1-minute period, 1 evaluation period, and treats missing data as notBreaching — a quiet minute on a low-traffic demo API isn't evidence of a problem. All four notify a single SNS topic.

Demonstration mechanisms

Generate real signals on demand

GET /work supports two query parameters that exist solely for demonstration and testing — never ship a caller-controlled failure/delay switch in a real API.

Latency simulation

GET /work?delayMs=2000

The handler awaits a bounded delay, clamped server-side to a maximum of 5000ms, before responding. Drives API Latency and Lambda Duration up for that minute.

Failure simulation

GET /work?fail=true

The handler logs a structured ERROR entry, then throws. This produces a Lambda Errors data point and an API Gateway 502 (counted in 5XXError) — one simulated failure, two real signals.

CloudWatch Logs Insights

Query the structured logs directly

These queries match the JSON log fields shown earlier.

Errors, most recent first

fields @timestamp, requestId, message, route, statusCode
| filter level = "ERROR"
| sort @timestamp desc
| limit 50

Slow requests

fields @timestamp, requestId, route, durationMs
| filter durationMs > 1000
| sort durationMs desc
| limit 50

One request, full story

fields @timestamp, level, message, requestId, route, durationMs
| filter requestId = "REQUEST_ID_HERE"
| sort @timestamp asc

SNS notifications

Alarms notify a single SNS topic

No email address is hardcoded anywhere in this project. Subscribe one optionally at deploy time: 

npx cdk deploy -c alarmEmail=you@example.com

SNS email subscriptions require confirmation. Check the inbox for a confirmation link — no notifications are delivered until it's clicked.

Cost & production readiness

Observability has a cost — and a ceiling on how far this sample goes

Cost drivers

API requests, Lambda invocation/duration, CloudWatch Logs ingestion & storage, custom metric storage, one dashboard, four alarms, SNS notifications. More telemetry is not automatically better telemetry — see docs/cost-considerations.md.

Recommended for production

Authentication, WAF, error-rate (not absolute) alarms, p90/p95/p99 latency, SLOs/SLIs, AWS X-Ray or OpenTelemetry tracing, centralized logging, incident tooling integration. See README production section.
